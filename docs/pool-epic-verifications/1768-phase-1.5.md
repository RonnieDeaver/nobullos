## Why those numbers cannot be real single-statement holds

1. Neon's statement-timeout for this DB is **210 000 ms**. A single
   query held for 662 482 ms would have been aborted by Postgres
   long before being recorded.
2. The project's own DB Hold Rules (replit.md) cap an individual
   hold at 10 s with a warning at 30 s.
3. `labelStats` in `server/db.ts` (`recordLabelStat`, lines 78–114)
   tracks a per-label **running maximum since process start**, with
   no decay, no rolling window, and no reset on process boot. The
   sampler's `byMaxMs` snapshot is therefore the running max of
   anything ever observed since the most recent deploy.
4. A long-running multi-statement transaction (or a worker that does
   non-DB work between two queries while still holding the
   connection) can plausibly hold a single label for tens of
   seconds. Multiple such holds get **aggregated as a single max**
   by `recordLabelStat`. So values just above the statement timeout
   (e.g. 101 053 ms) likely come from real transaction batches
   where the wall-clock-held label exceeded a single statement's
   timeout; values **well above** the statement timeout (the
   662 482 ms entries) cannot have any single-statement explanation
   and must be running-top-N artifacts from earlier process
   lifetimes.

## Outcome verdict (provisional pending Stage 1 rollups)

**Outcome A — stale running-top-N carryovers**, *plus* a known set
of "long but real" holds in the 60–100 s range that violate the 10 s
SLO and need to be staged out of the hold window. Concretely:

- Values **> 210 000 ms** in `top_hold_labels.byMaxMs` are
  mechanically impossible single-statement durations and are
  attributed to the un-windowed running-top-N (Outcome A).
- Values **between 30 000 and 210 000 ms** (the 74 011 / 84 229 /
  101 049 / 101 053 / 101 055 / 101 057 cluster) are most likely
  real multi-step worker holds and should be confirmed against
  `db_hold_label_rollups.max_duration_ms` once Stage 1 has produced
  rollups. If the rollup max for the same label is also > 10 s in
  the post-Stage-1 hour, escalate to a follow-up task **per label**
  (Outcome B for that label only) — do not block Stage 3.

## Required follow-up tasks (regardless of outcome)

1. **(Outcome A always applies)** File a small task: window or
   periodically reset the running-top-N in `server/db.ts`'s
   `labelStats` so `pool_state_samples.top_hold_labels.byMaxMs`
   reflects only the last N minutes, not lifetime-of-process. Add a
   note to the operator runbook section of `replit.md` explaining
   how to interpret pre-fix `top_hold_labels` rows.
2. **(API tenancy violation, independent of Stage 2 outcome)** The
   `worker:`-prefixed labels appearing in the API-pool top-N
   (`worker:semrush_background_refresh:enrich_campaigns`,
   `worker:google-drive-sync`, `worker:retroactive_reprocess`)
   indicate API-pool tenants that should be on the worker pool.
   Stage 3 (`db_pool_tenancy_enforcement_enabled = true`) is the
   right cover for the common path; if those labels persist on the
   API pool after Stage 3 finishes, file a per-label follow-up.

## Gate to Stage 3

Stage 3 may proceed when **either** (a) every label in the table
above resolves to Outcome A, **or** (b) labels that resolved to
Outcome B have follow-up tasks filed and do not implicate the
tenancy enforcement path. Do **not** gate Stage 3 on those
follow-ups landing — they're independent fixes.
